# ADR-0007: Grafana for live monitoring, dashboards generated as code

- **Status:** Accepted
- **Date:** 2026-10-07

## Context

Phase 3 produces SPC alarms, excursion detection results and root-cause rankings, but the only
way to see them is SQL or a Markdown report. A fab engineer watches control charts and gets
paged when a chamber drifts; a yield engineer reviews an excursion on one screen. Grafana and
Power BI are the two tools German fab job ads ask for. Power BI covers yield reporting from
the star schema (phase 7, ADR-0004); this decision is about the operational side.

Dashboards built in a UI drift: a panel changes, nobody knows why, and the next environment
looks different. Grafana's JSON is hundreds of lines per dashboard, and hand-edited JSON has
the same problem in a less readable form.

## Options considered

1. **Grafana, dashboards saved from the UI and exported.** Quick to start; the JSON is
   unreviewable (every drag changes dozens of lines), and SQL is buried in strings.
2. **Grafana, dashboards generated from Python.** One small module (`dashboards/build.py`)
   with helpers for panels, overrides and variables; the JSON is a build artefact checked
   into git. Same idea as Grafonnet or grafanalib, without another dependency.
3. **Streamlit or Dash.** Full control in Python, but it is a web app to maintain, has no
   alerting, and is not what fabs run.
4. **Superset / Metabase.** BI tools; good for ad-hoc questions, weaker for time series and
   alerting, and they overlap with Power BI.

## Decision

Grafana, provisioned entirely from git: datasource, dashboards (generated by option 2, written
with sorted keys so the diff is stable) and unified alerting rules with a webhook contact
point. Grafana reads TimescaleDB as `grafana_reader`, a role that can only `SELECT`.
Expensive panels read pre-computed data: a TimescaleDB continuous aggregate for daily sensor
rollups, and the dbt marts for everything else.

## Consequences

- **Reviewable and reproducible:** `make up` gives the same three dashboards and two alerts
  on any machine; a unit test fails if the committed JSON differs from the generator, and
  another checks that alert links point at real dashboards and panels.
- **Tested without Grafana:** `dashboards/sql.py` expands the Grafana macros the dashboards
  use and an integration test runs every variable, panel, annotation and alert query on the
  dev fab as `grafana_reader`. The price is a deliberately small macro set; a new macro has
  to be added there first.
- **Read-only by construction:** a dashboard query can't change data (tested). New schemas
  need grants: migration 0006 for `public` and `marts`, dbt `+grants` on rebuilt tables.
- **SQL does some SPC work:** the EWMA panel uses a custom `ewma()` aggregate as a window
  function, tested to match the Python chart exactly. Alarms themselves still come from the
  Python engine, which stays the single source of truth.
- **Alerts on simulated history:** the rules look at the latest day or week *of data*, not
  `now()`, or they would never fire on the demo fab. A real deployment would switch to
  relative time ranges.
- **Not covered:** no Grafana-side auth, users or folders beyond the one provisioned folder;
  the webhook sink only logs notifications.
